# PR Map 평가

정답을 아는 PR로 PR Map을 돌려서, 핵심 동작을 얼마나 찾는지와 토큰을 얼마나 쓰는지를 숫자로 잽니다. GitHub 액션 없이 로컬에서 돌립니다.

## 빠른 시작

```bash
node --import tsx eval/run.ts
```

정답지만 확인하고 분석은 하지 않습니다. 케이스마다 임시 저장소를 만들고 수집까지 한 뒤, 정답지의 줄 번호와 상태가 실제 코드와 맞는지 봅니다. 비용이 들지 않습니다.

```bash
node --import tsx eval/run.ts --yes
```

분석까지 실행합니다. 결과는 `eval/results/<라벨>/<케이스>/run-<n>/`에 저장됩니다.

```bash
node --import tsx eval/score.ts
```

저장된 결과를 지금 정답지로 다시 채점하고, 라벨별 평균 ± 표준편차를 `eval/results/summary.md`에 씁니다.

## 비용

실행할 때마다 분석에 쓴 토큰이 차감됩니다. 시작할 때 어느 쪽으로 차감되는지 출력합니다.

- `ANTHROPIC_API_KEY`가 없으면 로그인한 계정의 사용 한도에서 차감됩니다.
- `ANTHROPIC_API_KEY`가 있으면 API 요금으로 청구됩니다.

`추정 비용`은 API 요금으로 환산한 값입니다. 구독으로 돌려도 표시되지만 실제 청구액은 아닙니다. 실행 한 번의 상한은 `--max-budget-usd`(기본 5)로 정합니다.

## 옵션

| 옵션                   | 기본값         | 설명                                                 |
| ---------------------- | -------------- | ---------------------------------------------------- |
| `--yes`                | 없음           | 분석까지 실행합니다. 없으면 정답지만 확인합니다      |
| `--case <이름>`        | 모든 케이스    | 여러 번 쓸 수 있습니다                               |
| `--runs <n>`           | 1              | 케이스마다 반복할 횟수. 결과가 흔들리므로 2~3을 권장 |
| `--skill <폴더>`       | `skill/pr-map` | 평가할 스킬 폴더. 이전 버전과 비교할 때 바꿉니다     |
| `--label <이름>`       | `current`      | 결과를 저장할 이름                                   |
| `--model <모델>`       | `sonnet`       | 분석 모델                                            |
| `--max-turns <n>`      | 80             | 분석 에이전트의 최대 턴 수                           |
| `--max-budget-usd <n>` | 5              | 실행 한 번의 추정 비용 상한                          |
| `--keep`               | 없음           | 임시 저장소를 지우지 않고 경로를 출력합니다          |

분석은 자동 실행(`action/providers/claude.sh`)과 같은 프롬프트와 도구 권한으로 돌립니다. 다만 `--bare` 대신 `--safe-mode`와 `--strict-mcp-config`로 개인 설정, 스킬, MCP 서버를 끕니다. `--bare`는 API 키로만 로그인하기 때문입니다.

## 이전 버전과 비교하기

```bash
git worktree add ../pr-map-old <커밋>
node --import tsx eval/run.ts --yes --runs 3 --skill ../pr-map-old/skill/pr-map --label old
node --import tsx eval/run.ts --yes --runs 3 --label new
node --import tsx eval/score.ts old new
```

## 지표

| 지표             | 뜻                                                                          |
| ---------------- | --------------------------------------------------------------------------- |
| 검증 통과        | 분석이 끝난 뒤 `validate`를 통과한 비율                                     |
| 수정 횟수        | 검증에 실패해 고친 횟수 (0~3)                                               |
| 필수 동작 재현율 | 정답지의 `must` 동작 중, 근거 줄이 겹치는 노드가 있는 비율                  |
| 전체 재현율      | 모든 정답 동작 중 찾은 비율                                                 |
| 상태 일치        | 찾은 동작 중 노드의 `change`가 정답과 같은 비율                             |
| 변경 줄 커버리지 | 지도 대상 파일의 바뀐 줄 중 어떤 노드의 근거와라도 겹치는 비율              |
| 강등 비율        | 근거를 맞추지 못해 `unverified`가 된 노드의 비율                            |
| 정답지 밖 노드   | 바뀐 노드 중 정답지의 어떤 근거와도 겹치지 않는 노드 수. 틀렸다는 뜻은 아님 |
| 입력·출력 토큰   | 입력은 캐시 읽기·쓰기를 포함한 합                                           |

한계가 있습니다.

- 줄 겹침 재현율과 상태 일치는 **근거 줄이 겹치는지로만** 판정합니다. 설명 문장의 뜻과 `forbidden` 위반은 아래 "채점기"가 따로 판정합니다.
- 함수 전체를 근거로 잡은 노드 하나가 여러 동작과 겹치면, 그 동작들을 모두 찾은 것으로 셉니다.

## 케이스 추가하기

케이스는 `eval/cases/<이름>/` 폴더 하나입니다.

**직접 만드는 케이스:** `base/`와 `head/`에 바꾸기 전과 후의 파일을 넣습니다. 실행할 때 이 두 폴더로 커밋 두 개짜리 임시 저장소를 만듭니다. 정답을 먼저 정하고 코드를 쓰면, 정답지를 따로 검토할 필요가 거의 없습니다.

**실제 PR 케이스:** 폴더에 `answer.json`만 두고 `github`에 저장소, PR 번호, head 커밋을 적습니다. 실행할 때 저장소를 클론하고 `gh`로 PR을 수집합니다. PR head가 정답지와 다르면 멈춥니다.

`answer.json` 형식은 `answer.schema.json`에 있습니다.

```json
{
  "description": "이 PR이 무엇을 바꾸는지 한 문장",
  "behaviors": [
    {
      "id": "fetch-fail-clear-cache",
      "text": "불러오기에 실패하면 캐시 삭제를 시도하고 원래 오류를 다시 던진다",
      "change": "added",
      "evidence": ["h:src/profile.ts:11-13"],
      "must": true
    }
  ],
  "forbidden": ["캐시가 반드시 지워진다고 쓰면 틀림 (삭제 실패는 무시한다)"]
}
```

- `evidence`는 PR Map 근거와 같은 짧은 형식이지만, 경로를 항상 씁니다. `h`는 바뀐 뒤, `b`는 바뀌기 전 코드입니다.
- 항목 하나에 분기나 결과 하나를 씁니다. 줄 범위는 그 동작을 직접 보여 주는 최소 범위로 잡습니다.
- 실제 PR의 정답지는 PR Map 결과를 보기 전에 diff만 보고 씁니다. 결과를 먼저 보면 그 답에 끌려갑니다.
- 정답지를 쓰거나 고친 뒤에는 `node --import tsx eval/run.ts --case <이름>`으로 줄 번호를 확인합니다.

## 스킬 없이 돌려 비교하기

```bash
node --import tsx eval/run.ts --yes --baseline
```

같은 모델에 같은 저장소를 주되, PR Map의 지시문, 줄 번호 diff, 검증 없이 분석하게 합니다. 분석 대상 파일 목록과 출력 형식(`.pr-map/baseline.json`)만 알려 줍니다. 결과는 라벨 `baseline`에 저장되고, 같은 정답지와 같은 채점기로 채점합니다. 근거 줄이 실제로 있는지와 분기 상태가 근거와 맞는지는 `validate`와 같은 규칙으로 따로 셉니다.

## 채점기

```bash
node --import tsx eval/judge.ts
```

저장된 결과(`evidence.json`)를 다른 모델로 채점해 `judge.json`을 씁니다. 분석을 다시 돌리지 않습니다. `evidence.json`에는 노드 문장과, 근거 줄 번호로 git에서 읽은 실제 코드가 들어 있습니다.

- **노드 판정:** 문장마다 근거 코드가 문장을 뒷받침하는지 봅니다. `correct`(맞음), `partial`(과장이나 누락), `wrong`(코드와 모순), `unsupported`(이 근거로는 확인할 수 없음) 중 하나입니다.
- **정답 동작 판정:** 정답 동작마다 같은 뜻의 설명이 있는지 봅니다. `same`, `partial`, `missing` 중 하나입니다. 근거 줄이 겹치는 노드를 후보로 주고, 없으면 모든 노드에서 찾게 합니다.
- **틀린 주장:** `forbidden`에 적은 주장을 실제로 하는 문장이 있는지 봅니다.
- 판정마다 기본 3번 묻고 다수결로 정합니다. 채점 모델은 도구 없이 준 문장과 코드만 봅니다.

| 옵션               | 기본값 | 설명                                 |
| ------------------ | ------ | ------------------------------------ |
| `<라벨...>`        | 전체   | 채점할 라벨                          |
| `--case <이름>`    | 전체   | 여러 번 쓸 수 있습니다               |
| `--model <모델>`   | `opus` | 채점 모델. 분석 모델과 다르게 둡니다 |
| `--votes <n>`      | 3      | 판정마다 묻는 횟수                   |
| `--chunk-size <n>` | 12     | 한 번에 묻는 노드 수                 |
| `--force`          | 없음   | 이미 채점한 실행도 다시 채점합니다   |

주의할 점이 있습니다.

- **채점 비용이 분석 비용보다 큽니다.** 노드 300개를 Opus로 3번씩 채점하는 데 추정 $10어치가 들었습니다. 분석 12번은 $2.7어치였습니다.
- **채점기를 사람 판정과 맞춰 보지 않았습니다.** 판정 기준이 얼마나 엄격한지 확인되지 않았으니, 절대값보다 같은 채점기로 잰 두 결과의 차이를 보는 용도로 씁니다.

## 실제 PR 케이스

`pf-*` 케이스는 공개 저장소 `soma-376/pulsemetry-frontend`의 머지된 PR입니다. 정답지는 diff만 보고 AI가 쓴 초안이고, 줄 번호와 상태 규칙만 자동으로 확인했습니다. **사람이 내용을 확인하지 않았습니다.**

| 케이스  | 규모 | 변경 파일 | 지도 대상 파일 | 지도 대상 변경 줄 |
| ------- | ---- | --------- | -------------- | ----------------- |
| `pf-39` | 소   | 3         | 1              | 35                |
| `pf-59` | 소   | 7         | 3              | 98                |
| `pf-44` | 중   | 15        | 7              | 212               |
| `pf-40` | 중   | 24        | 7              | 808               |
| `pf-29` | 대   | 31        | 11             | 418               |
| `pf-30` | 대   | 44        | 22             | 1,478             |

규모는 변경 파일 수 기준입니다(소 1~7개, 중 8~25개, 대 26~60개). 테스트와 문서가 빠져서 지도 대상 파일은 그보다 적습니다.
